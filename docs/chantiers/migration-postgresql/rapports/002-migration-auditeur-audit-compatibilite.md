# 002 — migration-auditeur — Audit de compatibilité MariaDB → PostgreSQL 18

- Tâche : T3
- Date : 2026-10-18
- Statut : terminé

## Objectif
Recenser, en lecture seule, tout ce qui dépend de MariaDB/MySQL dans MangaTrackr (mapping,
requêtes, migrations, infra, versions), qualifier l'impact d'un passage à PostgreSQL 18, et
proposer un découpage de T4 (schéma et infra) et T5 (données) ainsi que les décisions à faire
trancher.

## Ce qui a été fait
- Lecture de `src/Entity/*` (18 entités, 2 enums), `src/Repository/*`, des services, contrôleurs,
  commandes, authenticators, contrôleurs EasyAdmin, fixtures et tests (recherche des requêtes,
  fonctions SQL, `LIKE`, tris, `findOneBy` sur des chaînes).
- Lecture de `config/packages/{doctrine,doctrine_migrations,messenger,security,framework}.yaml`,
  `.env`, `.env.test` (pas `.env.local`), `docker-compose.yml`, `docker/Dockerfile`,
  `docker/docker.sh`, `docker/mariadb/init/01-create-test-database.sh`, `.devcontainer/*`,
  `.github/workflows/ci.yml`, `Makefile`, `composer.json`, `phpstan.dist.neon`, des 15 migrations.
- Lecture des `CREATE TABLE` / `ALTER TABLE` du dump (aucune donnée recopiée). Comptages agrégés
  sur les `INSERT` par un script de scratchpad (seuls des nombres ont été produits).
- `composer show` (versions Doctrine), `php -m` (extensions), lecture du code de sélection de
  plateforme de DBAL et de la stratégie d'identifiants de l'ORM dans `vendor/`.
- `php bin/console doctrine:mapping:info` (18 entités OK) et `doctrine:schema:validate --skip-sync`
  (mapping correct).
- `doctrine:schema:create --dump-sql` avec une `DATABASE_URL` PostgreSQL : **échec** (`could not
  find driver`, la commande se connecte). Contournement : script de scratchpad qui construit
  l'EntityManager sur une connexion DBAL `pdo_pgsql` `serverVersion=18` **interdite de connexion**
  (wrapper qui lève une exception sur `connect()`) et produit le DDL du mapping, en stratégie
  SEQUENCE et IDENTITY. Aucune base n'a été contactée. Fichiers temporaires dans le scratchpad
  (non versionnés).
- Recherche web : support PostgreSQL 18 de DBAL, changement de volume de l'image `postgres:18`.

Aucun fichier du dépôt modifié hormis ce rapport et une ligne de `journal.md`.

## Résultats

### Versions et plateforme
| Élément | Constat |
|---|---|
| `doctrine/dbal` | 3.10.6 |
| `doctrine/orm` | 2.20.13 |
| `doctrine/doctrine-bundle` | 2.19.1 ; `doctrine/migrations` 3.9.8 ; `doctrine-migrations-bundle` 3.7.1 |
| `symfony/doctrine-messenger` | 6.4.48 (transport Doctrine, `use_notify: true`) |
| PHP du conteneur | 8.2.34, extensions `pdo_mysql`, `pdo_sqlite` ; **pas de `pdo_pgsql`** |
| OS du conteneur | Debian 13 (trixie) : le paquet `postgresql-client` y est en 17 |

Plateforme sélectionnée avec `serverVersion=18` : `AbstractPostgreSQLDriver::createDatabasePlatformForVersion`
retourne **`PostgreSQL120Platform`** pour toute version >= 12 (vérifié en exécution :
`Doctrine\DBAL\Platforms\PostgreSQL120Platform`). Il n'existe pas de plateforme plus récente en
DBAL 3. Aucun problème connu spécifique à PG 18 trouvé pour DBAL 3.10 (recherche non
concluante, pas d'issue dédiée) : **à confirmer en T4** par `doctrine:schema:validate` et un
`doctrine:migrations:diff` vide sur un vrai PG 18 (pas de diff perpétuel, notamment sur le défaut
d'enum de `manga.category`).

Pièges connus :
- ORM 2.20 + PostgreSQL + `GeneratedValue` AUTO : stratégie **SEQUENCE** par défaut, avec une
  dépréciation (`doctrine/orm#8893`) tant que `identity_generation_preferences` n'est pas configuré.
- DBAL 3 : IDENTITY produit `SERIAL` (et non `GENERATED BY DEFAULT AS IDENTITY`, réservé à DBAL 4).
- Image `postgres:18` : le volume déclaré devient `/var/lib/postgresql` (PGDATA
  `/var/lib/postgresql/18/docker`) ; monter un volume sur `/var/lib/postgresql/data` échoue au
  démarrage.
- `pg_dump`/`psql` doivent être en version >= serveur : le client de trixie (17) ne suffit pas,
  il faut le dépôt PGDG (`postgresql-client-18`) si on veut ces outils dans `app`.

### DDL PostgreSQL 18 généré depuis le mapping (sans connexion)
- 18 tables + 3 tables de jointure, 104 instructions (IDENTITY) / 122 (SEQUENCE, 18 `CREATE
  SEQUENCE <table>_id_seq`).
- Types : `int(11)` → `INT`/`SERIAL`, `tinyint(1)` → `BOOLEAN`, `datetime` → `TIMESTAMP(0) WITHOUT
  TIME ZONE`, `longtext` → `TEXT`, `double` → `DOUBLE PRECISION`, `json` (longtext + CHECK) →
  `JSON`, enum `category` → `VARCHAR(100) DEFAULT 'Unknown' NOT NULL`. Longueurs identiques.
- La table `user` est **auto-citée par DBAL dans le DDL** (`CREATE TABLE "user"`), mais pas dans
  le SQL généré par l'ORM (DQL, persisters), qui n'applique les guillemets que si le mapping les
  demande : `SELECT ... FROM user u0_` et `INSERT INTO user` échouent sur PostgreSQL.
- Index de `manga_tenrai_api` : le mapping génère `UNIQ_8A6250027B6461` / `FK_8A6250027B6461`
  alors que la prod a gardé `UNIQ_A2733E8C7B6461` (hachage de l'ancien nom `manga_jikan_api`,
  écart déjà relevé en T2). Une baseline PG générée depuis le mapping corrige d'office cet écart
  et celui des index de `messenger_messages` (table créée par le listener de schéma Messenger).

### Réponses aux points particuliers

**1. DBAL 3.10.6 et PostgreSQL 18.** `serverVersion=18` → `PostgreSQL120Platform` (dernière
plateforme PG de DBAL 3). Le DDL généré est correct pour PG 18. Pièges : stratégie d'ID implicite
(SEQUENCE + dépréciation), `SERIAL` au lieu d'`IDENTITY` natif, `user` non cité côté ORM. Aucun
problème connu propre à PG 18 identifié, à confirmer en T4 sur un serveur réel (schema:validate,
diff vide).

**2. Migrations : recommandation = nouvelle baseline PostgreSQL unique** (candidate ADR).
- Les 15 migrations sont du SQL MySQL brut, sans garde de plateforme : impossible de les rejouer
  sur PG sans les réécrire, ce que la règle du projet interdit.
- Baseline : une seule migration `VersionAAAAMMJJ…` générée sur une base PG vide
  (`doctrine:migrations:diff`, avec le listener Messenger), précédée d'un
  `abortIf(!$platform instanceof PostgreSQLPlatform)`. Elle corrige les écarts d'index hérités.
- Les 15 anciennes sont retirées de `migrations/` (déplacées hors du chemin de migrations, par ex.
  `migrations/archive-mariadb/` exclu de `migrations_paths`, ou simplement laissées dans
  l'historique git) : **c'est une exception explicite à la règle « ne jamais modifier une
  migration commitée »**, à acter par ADR.
- `doctrine_migration_versions` n'est pas transférée en T5 : la base PG ne contient que la version
  de la baseline (créée par `migrations:migrate` sur base vide).
- Conséquence : à partir de la fusion, `migrations/` ne s'applique plus à la prod MariaDB ;
  donc **gel du schéma de prod** jusqu'à la bascule, et ne pas déployer la branche PG sur
  Hostinger (D6).
- Alternative écartée : conserver l'historique avec des migrations doubles (MySQL/PG) — exige de
  modifier les migrations commitées, sans bénéfice puisque la prod repartira d'un import.

**3. Comparaisons sensibles à la casse.** Changements réels : recherche catalogue (#12, casse et
accents), dédoublonnage MangaUpdates (#13), connexion/reset/OAuth par email et unicité des emails
(#15, #16), tri alphabétique (#17). Sans impact : slugs (générés en minuscules, données propres),
`findOneByNameSlug('terms-of-use')`, catégories (valeurs d'enum exactes). EasyAdmin applique déjà
`LOWER(...) LIKE` sur PG (vérifié dans `vendor/easycorp/.../Orm/EntityRepository.php:123-128`),
donc la recherche admin reste insensible à la casse mais devient sensible aux accents.

**4. Identifiants.** Défaut ORM 2.20 sur PG = SEQUENCE (séquences `<table>_id_seq` non liées aux
colonnes, `nextval` lu par l'ORM avant chaque insert, colonne `id INT` sans défaut).
IDENTITY en DBAL 3 = `SERIAL` (séquence `<table>_id_seq` possédée par la colonne, défaut
`nextval`). **Recommandation : IDENTITY explicite** (`identity_generation_preferences:
{ Doctrine\DBAL\Platforms\PostgreSQLPlatform: identity }`) : sémantique la plus proche
d'AUTO_INCREMENT, inserts SQL manuels possibles, un aller-retour de moins, et c'est le défaut
d'ORM 3. Dans les deux cas : le transfert insère les ID explicites, puis **chaque séquence doit
être recalée**, par exemple `SELECT setval(pg_get_serial_sequence('"user"', 'id'),
GREATEST(MAX(id), <AUTO_INCREMENT> - 1))` (ou `setval('<table>_id_seq', …)` en SEQUENCE), avec la
valeur AUTO_INCREMENT du dump pour **ne pas réutiliser d'ID supprimés** (la scanthèque du
`localStorage` référence des ID `manga_user_track`). Tables vides : laisser la séquence à 1.
Contrôle : un insert de test après recalage, puis rollback.

## Écarts, risques, points non vérifiés
- **Non vérifié sur un vrai PostgreSQL** : aucun serveur PG ni `pdo_pgsql` disponible. Le DDL a
  été produit hors connexion ; le comportement à l'exécution (diff perpétuel, NOTIFY Messenger,
  tris, `LIKE`) reste à confirmer en T4/T6.
- `doctrine:schema:create --dump-sql` ne fonctionne pas sans driver : le contournement par script
  n'utilise pas exactement la configuration du bundle (même stratégie de nommage, même
  répertoire de mapping, mais sans le listener Messenger, donc sans `messenger_messages`).
- MariaDB était injoignable au début de T3 : aucun `schema:validate` ni requête faits par moi ;
  je me suis appuyé sur le rapport 003 pour l'état de la base importée.
- Les comptages sur le dump viennent d'un analyseur maison des `INSERT` ; ses totaux de lignes
  recoupent exactement `001-attendu.json` pour les 10 tables lues.
- Recherche web sur DBAL + PG 18 non concluante (pas de problème connu trouvé, ce qui ne prouve
  pas qu'il n'y en a pas).
- La CI ne fournit pas `DB_USER_PASSWORD` alors que `.env.test` l'utilise : je n'ai pas vérifié si
  la CI passe aujourd'hui.
- `inventaire.php` gère déjà `pgsql` (citation, booléens normalisés en `1`/`0`, JSON normalisé) ;
  écarts attendus et justifiables : `doctrine_migration_versions` (contenu différent par
  construction) et éventuellement `messenger_messages` (vide des deux côtés).

### Décisions à faire trancher par l'utilisateur (candidates ADR)
- **D1 — Migrations** : nouvelle baseline PG unique et archivage des 15 migrations MySQL
  (exception à la règle « ne jamais modifier une migration commitée »). Recommandé.
- **D2 — Table `user`** : citation `` `user` `` (même nom partout, aucune migration MariaDB,
  transfert direct ; piège : `SELECT * FROM user` en psql renvoie l'utilisateur courant sans
  erreur) **ou** renommage `app_user` (plus propre, mais nom différent entre source et cible et
  migration MariaDB si la prod doit suivre). Recommandation : citation pour ce chantier.
- **D3 — Identifiants** : IDENTITY (`SERIAL` en DBAL 3, recommandé) ou SEQUENCE ; dans les deux
  cas, configuration explicite et recalage des séquences.
- **D4 — Recherche insensible à la casse et aux accents** : `LOWER() LIKE` seul (perd
  l'insensibilité aux accents actuelle) / extension `unaccent` + fonction DQL / collation ICU non
  déterministe sur les colonnes de titre (PG 18 accepte `LIKE` sur ces collations) / `citext`
  pour les emails. Recommandation : `LOWER()` + normalisation des emails maintenant ; accents à
  décider selon l'usage.
- **D5 — Collation/locale de la base PG** (tri des titres) : ICU `fr` ou `und`, libc
  `fr_FR.UTF-8`, ou `C.UTF-8`. Recommandation : ICU, fixée à `initdb`/`CREATE DATABASE`.
- **D6 — Coexistence** : garder MariaDB et PG côte à côte jusqu'à la fin de T5 ; gel du schéma de
  la prod Hostinger et pas de déploiement de la branche PG sur Hostinger avant la bascule.
- **D7 — `json` ou `jsonb`** : `json` recommandé (texte conservé, aucune requête JSON).
- **D8 — `disable_type_comments: true`** dès la baseline (évite une migration de commentaires au
  passage à DBAL 4) : optionnel.
- **D9 — Outil de transfert** : script PHP/DBAL (recommandé, 71 029 lignes) ou `pgloader`
  (conteneur supplémentaire, à brider en mode « data only »).
